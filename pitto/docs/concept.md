# PITTO コンセプト

> PITTO(ピット) ※仮称 — 商標・ドメイン確認前のため名称は仮称。

「空いている場所に、その場でサッと停める」をコンセプトとする、
**予約不要・設備不要のマイクロ駐輪場プラットフォーム**。

管理者は無駄なスペースを提供でき、利用者はスマホで簡単に決済でき、安い料金で借りられる。

## 最重要思想

PITTOは「駐輪場を予約するサービス」ではない。
**「街中の小さな空きスペースを、その場で使える駐輪場に変えるインフラ」** を目指す。

| 利用者にさせないこと | オーナーにさせないこと |
| --- | --- |
| 予約 | 毎日の予定設定 |
| 予定の入力 | 予約の管理 |
| アプリのインストール | 利用者との連絡 |
| 大量の個人情報の入力 | 機械の購入 |

利用者は、空いている区画を見つけ、QRを読み、停める。
**この単純さを壊す機能は、原則追加しない。**

## 既存サービスとの差

### 予約型シェアサービス (akippa / みんちゅうSHARE-LIN)

事前に場所を探し、日時を決めて予約する体験が中心。自動車には適している。
しかし自転車は「目的地まで来た → 近くに停めたい → 空いている場所を見つけた → 今すぐ停めたい」
という突発利用が多い。そのため PITTO では**予約という概念を原則なくす**。

| 採用する | 採用しない |
| --- | --- |
| 空きスペース活用 | 貸出日の設定 |
| 設備不要 | 事前予約 |
| 成果報酬 | 予約枠 |
| 小規模スペース | 日程管理 |

### MINIPA

自転車専用・1台分から登録可能・設備投資不要という点は参考にする。
ただし MINIPA が1日単位・月極中心なのに対し、PITTO は
**30分・1時間・3時間程度の短時間利用**を中心とする。

### PARKING PAY

今回の構想に最も近い。予約不要・1台から運用・精算機不要・フラップ不要・
キャッシュレス・時間貸しという考え方は積極的に参考にする。
ただし PITTO は自転車向けにもっと軽量化し、以下を削る。

- アプリ必須
- 車両ナンバー入力
- 車種登録
- 大型カラーコーン
- 車向けUI
- 複雑な検索操作

目標は「Webサイトを使っている」という感覚すら少なくすること。

### 既存QR駐輪場

電磁ロック・駐輪ラック・精算機・ゲート・センサーは数十〜数百台規模では有効だが、
「ビル横に5台」「店舗横に3台」「マンション前に8台」という規模では設備投資が重い。
PITTO では原則、**設備を置かない**。必要なのは 駐輪区画・番号・QRコード だけ。

## 差別化のまとめ

一言で言えば **「空きスペースを、その日から小さなコイン駐輪場に変える仕組み」**。

- **予約不要** — 未来の場所を確保するサービスではなく「今ここに停める」サービス
- **アプリ不要** — QRからブラウザを開く
- **駐輪機不要** — 電磁ロック・ゲート・精算機を必要としない
- **小規模特化** — 1〜20台程度を主対象とする
- **オーナー設定を最小化** — 毎週カレンダーを設定するような運営にはしない
- **自転車特化** — 車両番号・車種・車高など自動車向け情報を排除する

## 利用者体験

### 最重要UX

「駐輪場を検索してから利用する」より「現地でPITTOを見つけて使う」を中心とする。
そのため **QRコードを最重要導線**とする。

### 区画単位QR方式

「この駐輪場は5台」という管理だけでは、実際に自転車が停まっているか判定できない。
そこで各区画に番号を付け、それぞれ固有のQRコードを発行する。

```
PITTO TENJIN 01 / 02 / 03 / 04 / 05
```

### フロー

1. 空いているPITTO区画を見つける
2. 区画QRを読む
3. 画面に 場所・区画番号・料金 が大きく表示され、［この区画を利用する］を押す

### 初回利用

初回のみ最低限の本人識別を行う。電話番号またはメール認証(可能ならSMS優先)。
決済方法は Stripe で登録し、クレジットカード・Apple Pay・Google Pay に対応する。

名前・住所・生年月日・自転車写真などを大量に入力させない。

### 2回目以降

Cookieまたはログイン状態を保持する。
QR → 利用開始 → Apple Pay等 → 完了 を **30秒以内**に。

### 利用中・終了

利用中画面には 利用中 / 場所 / 区画 / 開始時刻 / 経過 / 現在料金 を大きく表示し、
最下部に［利用を終了する］を置く。

終了すると 料金計算 → Stripe決済 → 区画FREE → 完了画面 と進む。
**料金計算は必ずサーバー側で行い、クライアントから送られた金額は信用しない。**

## 運用上の課題への対応

### 出庫忘れ

このサービス最大の課題の一つとして最初から設計する。
利用開始から一定時間後(6時間・12時間・23時間)に Web Push・メール・SMS 等で
「まだ利用中ですか？」［利用中］［利用終了］を通知する。

### 逆パターン(システム上ACTIVEだが実際は空き)

別ユーザーが「区画は空いています」と報告できる。管理者画面へ通知する。
**即座に自動解除はしない。** 不正解除防止のため 写真・報告時間・報告ユーザー を保存する。

### 無断駐輪(システム上FREEだが自転車がある)

QRページに［無断駐輪を報告］を用意する。写真撮影 → アップロード → 運営へ通知。
オーナーにも通知する。

### 「満空情報」を過信しない

センサーがない以上、完全なリアルタイム満空情報とは表示しない。
検索画面では「空き 3区画」ではなく **「システム上の空き 3区画」** として扱い、
実際の現地状態とのズレが起こり得る設計にする。

## オーナー側

### コンセプト

「駐輪場経営をしてください」とは言わない。
伝える価値は **「余っている3㎡を貸してください」**。

対象: 個人宅 / 店舗 / ビル / マンション / 月極駐車場 / 会社 / 空きテナント /
建替え待ち土地 / 駐車場の余剰部分

### 登録

名称・住所・Google Maps位置・写真・利用可能台数 のみ。
MVPは自転車のみ。将来 原付・バイク・自動車 を追加できるDB構造とする。

### 権利確認

公共の土地や利用権限のない土地は登録させない。
登録時に「この場所を駐輪場として提供する権限があります」への同意を必須化する。
所有者本人でない場合は、所有者・管理者から許可を得ていることを確認する。
運営側が 登記関連資料・管理会社許可・賃貸契約・本人確認 を確認できる構造にする。

**MVPでも管理者審査を入れ、完全自動公開にはしない。**

### 営業時間

初期値は24時間利用可能。必要な場合だけ「毎日 9:00〜22:00」のような固定営業時間を設定できる。
MVPでは 曜日ごとの細かいカレンダー・日別設定・祝日設定 は作らない。
一時停止は［受付中］［停止］のスイッチだけ。

### 料金設定

MVPでは複雑な料金テーブルを禁止する。「60分100円 / 最大24時間500円」だけで料金体系を作れるようにする。
運営側から「周辺相場からの推奨料金」も設定できる構造にする。

### QR生成と現地設備

審査完了後、各区画用QRコードを自動生成する。
オーナーは［QRセットをダウンロード］でA4 PDFを取得する。
内容は PITTO / 空いていたらQRを読み取って利用開始 / 区画番号 / QR / 料金 程度に留め、
大量の説明文は載せない。

現地は 床または壁の区画番号 + QR表示 のみを基本構成とし、
必要に応じて ステッカー・小型看板・地面ライン・車輪止め を追加する。
専用機械を必須条件にしない。

### ダッシュボード

最初の画面で 本日の売上 / 現在利用中(3台 / 8台) / 今月売上 / 受付状態 を確認できること。
詳細画面で 区画・利用中・利用時間・売上・利用履歴・トラブル報告 を見られること。

### 売上

Stripe Connect等を前提に設計し、利用料金を PITTO手数料 + オーナー報酬 に分ける。
**手数料率はコードに固定せず、管理画面から変更可能にする。**

## 管理者(運営)画面

- **オーナー**: 一覧 / 本人確認 / 承認 / 停止
- **駐輪場**: 申請 / 審査 / 公開 / 非公開 / 強制停止
- **区画**: FREE / ACTIVE / FLAGGED
- **利用**: 利用中 / 完了 / 未払い / 長時間利用 / 異常
- **トラブル**: 無断駐輪 / 出庫忘れ / 写真 / オーナー報告 / 利用者報告
- **決済**: 売上 / 手数料 / オーナー報酬 / 未払い / 返金

## 検索

QR利用を中心とするが、地図からPITTOを探せる検索も作る。
表示は「PITTO 天神○○ / 徒歩2分 / 60分100円 / システム上 3区画利用可能」。

ただし **検索を主役にしない**。akippa型の 検索 → 比較 → 日時設定 → 予約 にはしない。
PITTOは 歩いている → PITTO発見 → QR → 利用 を最短導線とする。

## MVPで絶対に作らないもの

事前予約 / 予約カレンダー / 日別料金 / 繁忙期料金 / レビュー / ユーザー間チャット /
ポイント / クーポン / ネイティブアプリ / IoTセンサー / 電磁ロック / 精算機 / ゲート / AI機能

機能追加より **利用開始までの短さ** を優先する。

## UI方針

スマホファースト。ユーザー画面は極限までシンプルに。

基調色は 白 + 黒または濃紺 + アクセント1色。大きなボタン。文字を詰め込まない。
画面上部には常に 場所・区画・料金 を表示する。

## KPI

QRスキャン数 / QR→利用開始率 / 利用開始までの秒数 / 平均利用時間 / 区画稼働率 /
1区画あたり売上 / 出庫忘れ率 / 未払い率 / 無断駐輪報告率 / オーナー継続率

特に **「QRを読んでから利用開始まで何秒か」** を最重要KPIとする。

## 技術構成

Next.js / TypeScript / Tailwind CSS / Supabase / PostgreSQL / Supabase Auth /
Supabase Storage / Stripe / Stripe Connect / Google Maps Platform / QR生成ライブラリ

Webアプリとして構築する。PWA化できる構造にはするが、アプリインストールは要求しない。
